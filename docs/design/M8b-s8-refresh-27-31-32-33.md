## 1. Item 33: root cause, with evidence

The `.swiftUI` reset (`resetAnimation` default, D39) clears the hold inside `withAnimation(a)`
(`RefreshCoordinator.apply` l.281, `closeHold` l.411). `setRefreshHold(_, followsOffset: true)` writes target AND presentation
(`writeBoth`), so the state is at rest at once while `ContentTransform` (offset + insets in its `animatableData`) and
`RefreshPlacementEffect` (`pull`) are interpolated by SwiftUI (memory note "SwiftUI-animated reset jumps the presentation").

A finger during that animation:
1. `PanEnvironment.isMovingWithoutFinger` is false (phase `.idle`, no clock motion, no transaction token), so the touch is
   no catch; the drag starts from `presentationOffset` = the model at rest. First sample: model pull 7.8 (17.5) / 35.4 (27.0)
   while the content is drawn at pull 30.1 / 25.4.
2. The content effect drops SwiftUI's residual at the next update: 17.5 keeps it through the first (plain) update, the slow path
   clamps it at the animated inset (oy −317.87 → −310.13), the next unanimated finger write cancels it (oy −287.87, it 280.06):
   **the content jumps back** (video: 17.5 preserve band 30 → 8 in one frame, `catchcheck` dip 20.7 / 22.7 pt; 27.0 drops it at
   the first plain update: dip 25.3 pt; 27.0 `.stretch`: 18 pt). The jump was not reported before (the re-checks looked at the
   spinner only); it is the same defect.
3. 17.5 only: `RefreshPlacementEffect` keeps the residual through every tracking update (log: RP pull 37.87 = model 7.81 +
   30.06 residual, 36.69, 64.20 = 35.3 + 28.9, ... decaying with the 4 s ease-out) while the content has none: the indicator's
   box sits ~28 pt beyond the content's edge, so once the real pull is below ~39 the arrow is drawn over the content
   (frames 383, 395-403 at 09226f4 = item 33's 1.3-10.7 pt; spikelook control 323-331). 27.0 cancels the indicator's residual
   two updates after the content's (log: RP 25.45 / 25.15 with model 0, then 35.36 = model): no over frames there, but the jump.
4. Transactions seen at the catch (`.transaction` probes, 27.0): the content's first update after the touch is plain
   (`a 0 d 0`) at 09226f4; with the fix it is the catch's unanimated write (`a 0 d 1`) for the content AND the indicator
   (TXC/TXL `a 0 d 1`), and both cancel their residual in that update.

So item 33 is ours, not SwiftUI's: the catch does not catch what is drawn, and the two animatable effects then disagree about
the residual (OS-dependent). The fix removes the residual's meaning: the model becomes the drawn state at the catch, so whether
an effect keeps or cancels the remaining animation, it ends where it was drawn.

## 2. Item 33 design: catch where it is drawn

### 2.1 Mechanism (spiked as `-ZTronSpikeCatch`)
- `ZTronScrollState`: a **drawn-motion window**. `noteSwiftUIDrawnMotion()` opens it; the coordinator calls it right before
  each SwiftUI-animated hold clear (the D39 `withAnimation` in `apply`, the `.swiftUI` branch of `closeHold`).
  `drawnAway() -> (offset: CGPoint, zoom: CGFloat)?` returns `probe.pending` (the content effect's last drawn offset/zoom,
  lock-protected, one frame behind = the frame on the screen at the touch) while the window is open, no clock motion, no
  transaction token, not tracking, no resize open, the probe's size within 1 pt of the viewport, the same zoom (1e-4) and
  the drawn offset more than 0.5 pt from the presentation. The window closes in `beginIntervention()`, `cancelMotion()`,
  `scroll(to:)` (a transaction), and when `drawnAway()` finds the probe within 0.5 pt of the model (the animation ended).
  Production uses the window (not the bare probe test the spike used) so a steady drawn/model difference at rest (a slow-path
  clamp, `transform.clampedAtRest`) can never turn a tap into a catch (a catch locks the content for that touch).
- `PanCoordinator.peekEnvironment()` (l.164) and the pinch environment (l.392):
  `isMovingWithoutFinger = (decelerating || animating) && !tracking || (!tracking && state.drawnAway() != nil)`.
  A touch during the reset is then a catch (`.catchMotion`), with what a catch implies (content locked for that touch,
  `caughtUndecided` for nested arbitration).
- `ZTronScrollState.interrupt()` (l.1440): when no motion / token runs and `drawnAway()` is non-nil, in a batch:
  `lastInterruptedVelocity = .zero`, `unanimated { writeBoth(offset: drawn.offset, zoom: drawn.zoom) }`, close the window.
  Then `beginDrag` rebases on the new presentation (the session re-reads the environment after `.catchMotion`), so the drag
  continues from where the content was drawn. The refresh engine's re-grab sees the drawn pull (the coordinator's
  `max(state, drawn)` while retracting is now the same number).
- The indicator: nothing to change when the content and the leaf cancel their residual in the catch's unanimated update
  (27.0 measured: they do). **17.5: see 2.3** (if the leaf keeps its residual there, the leaf draws the written pull after
  such a catch until its own interpolation has run out: `RefreshCatchFollow`, spiked).

### 2.3 The indicator after the catch (17.5)
17.5 differs from 27.0 in two ways, both read from the per-update log of the stretch run (`spikelook spikecatch spikelog`):
1. **The drag is not rebased on the catch.** 17.x has no touch-down before the pan's recognition (the gated observer is armed
   by the phase only), so `PanSession.handle(.dragChanged)` from `.idle` synthesizes the touch-down and recognizes in one call
   (l.198-201) with the environment read before the catch: `beginDrag` takes the baseline from the pre-catch presentation
   (the model at rest), and `PanCoordinator.handle` (l.253) applies `.catchMotion` and then that stale `.setOffset`. Log: CATCH
   drawn −312.63, then the first drag write −287.87 = rest + 7.81 (the model steps back 24.8 pt). 27.0 / 18+ / 15-16 catch at
   the touch-down (spatial / observer), one event before the recognition, so their `beginDrag` reads the caught presentation.
2. **SwiftUI 17.x keeps the reset's remaining animation through unanimated (`d 1`) writes** (27.0 cancels it): the content
   effect's input after the catch is the written value + 32.6 pt (`CT oy −345.30` for a model of −312.70; the slow path's
   clamp at the animated inset draws −312.70 for that frame), and the indicator's interpolation is model + 32.3-32.6 through
   the whole drag (`FOLLOW model 22.84 interp 55.15`). The spike's leaf-only latch (`SpikeCatchFollow`: the indicator draws the
   model pull after a catch) then disagreed with the content for 2 frames (the clip at the model's 7.8 pt gap: the spinner
   drawn 8 pt tall) and ~16 pt for 3 more (centred on the model's band while the content drew the residual on top). The
   preserve run did not show it (the gap's pull look after the re-grab, no carry), so the latch alone is not the design.
3. **The header keeps it too.** Its five effects animate the header offset `o′` (`HeaderLiveInput.offset`): `.stretch`
   draws D69's `HeaderStretchEffect` + `HeaderStretchClip` inside `HeaderSlotLayout`, `.preserve` `.followContent`
   translates with the pull (16+ `HeaderSlotLayout`, 15 / forced `HeaderTranslation` + `HeaderFallbackFrame`). After the
   catch they draw the written `o′` + the residual: in the `.stretch` run the header's bottom edge covers the content's top
   by the residual from the catch frame (f337: 32.5 pt, then 31.7 → 0.5 pt over 2.4 s, the 4 s ease-out's tail) while the
   content and the indicator draw the model. The same on 09226f4 without any spike (29.5 pt at most, f316-451, 2.2 s): a
   pre-existing 17.5 defect of item 33's cause, not listed before (27.0 preferred / forced: none). The pin run's
   "spinner not moved against a +32.66 band step" at f337 was this edge, not the spinner.

The design for every OS, so that whatever SwiftUI does with the remaining animation the drawing is the model:
- **Rebase after a catch in the same call** (`PanCoordinator.handle` l.253): apply the effects up to `.catchMotion`, re-read
  the environment, and when the session is now `.dragging`, `session.rebase(presentation:translation:env:)` (the existing
  one-finger-after-pinch rebase, l.170) and replace the call's `.setOffset` with the caught presentation. Only a catch that
  moves the presentation (the drawn catch) changes anything: a clock catch adopts the presentation the environment already had.
- **Pin every animatable effect that follows the offset to the model after a drawn catch** until SwiftUI's own
  interpolation reaches the model:
  `ContentTransform` (a stored, non-animatable copy of its `TransformVector` from `TransformHost`, drawn instead of
  `animatableData` while `catchSeq > clearSeq`; the effect ends the pin itself when the interpolation is within 0.01 pt /
  1e-5 of the copy: `CatchPin`, lock-protected like the probe, the effect may run off the main thread) and
  `RefreshPlacementEffect` (its `modelPull`, the same rule; `SpikeCatchFollow` generalized) and the header's five effects:
  `HeaderLiveInput` carries a non-animatable `catchPin` (the `CatchPin` and the model `o′`, set in
  `HeaderFrameModifier.wake()`), and `HeaderStretchEffect.effectValue`, `HeaderStretchClip.path`,
  `HeaderTranslation.effectValue`, `HeaderSlotLayout.placeSubviews` and `HeaderFallbackFrame.body` read
  `live.pinned(key)` (the model `o′` re-derived by `at(offset:)`) until their own interpolation reaches it, one latch per
  effect (they converge separately: the content's ended at its third evaluation, the header's after 2.7 s). Any future
  effect that animates the offset (i28's grown header, 10) takes the same pin. 27.0 / forced: a no-op (the
  interpolation equals the model at the first evaluation: measured, no PIN lines past the catch frame). A SwiftUI-animated
  write by the library (`noteSwiftUIDrawnMotion()`, the transaction path) bumps `clearSeq` and ends the pin before it animates.
- Spiked as `-ZTronSpikePin` (the rebase, the content pin and the header pin: `HeaderLiveInput.spikePin` /
  `spikePinned(_:)`, the five effects; the leaf keeps the spike's latch), 4 s ease-out reset, fling down into it:

### 2.4 Alternatives rejected
- **Make the reset a clock motion** (draw the content back on our clock, as `.uikit`): the `.swiftUI(Animation)` curve cannot be
  sampled on 15-16 (`Animation.animate(value:time:context:)` needs an `AnimationContext` nobody can create), so the app's
  animation would not be honoured; and D39 (the indicator in the same transaction as the content) would lose its reason.
- **Transaction path for the reset** (`scroll(to:)` inside `withAnimation`, probe-fed presentation): the inset change is not a
  scroll; presentation would trail the drawing by a frame and the leaf (which reads presentation) would lag the content by a
  frame during every reset (a seam of up to the frame's travel), which D39 removed.
- **Cancel the leaf's residual by forcing `disablesAnimations` on its update** (`.transaction` at the catch frame): it is the
  transaction SwiftUI gives the leaf that differs per OS (27.0 baseline: plain first, then `d 1`), so it would depend on
  update coalescing; the catch at the drawn state makes the residual irrelevant instead. Not needed on 27.0 (measured).
- **Change the phase to `.animating` during the reset** (so every existing catch path, the 17.x observer arming and the hit
  gate see it): changes the delegate and reader semantics of a refresh's end (an extra `didEndScrollingAnimation`, readers
  seeing `.animating` with a static offset). Not taken; 17.x catches at the pan's recognition instead of the touch-down (the
  gated observer is armed by the phase only), as a UIKit pan does; the content does not move under the finger after that.
- **The general probe test without a window** (the spike): would make any steady drawn/model difference at rest a catch.
- **Cancel SwiftUI's residual instead of pinning** (17+: wrap the reset's `Animation` in a `CustomAnimation` whose catch
  instance `shouldMerge`s and finishes at once): merging only happens between two animations of the same type on a value
  the catch's transaction changes; the hold's inset is not changed by the catch (its residual stays: the slow path's clamp
  of 2.3 (2)), 15-16 have no `CustomAnimation`, and the pin is needed there anyway if they keep the residual (11). Not
  spiked; the pin covers every effect with one rule and is a no-op where SwiftUI already cancels (27.0, measured).
- **Pin only the content and the indicator** (the first pin spike): the header's five effects then draw the residual
  over the content on 17.5 (2.3 (3): 32.5 pt for 2.4 s).

## 3. Items 32 and 31: the band's pull look and the engine's carried spinner

### 3.1 Placement math (`RefreshIndicatorMath.placement`, `holdsPlacement`)
- L1, band `.system`: the pull look is the refreshing look's centring: `center = s > 0 ? min(s, L)/2 : s − min(H − rest, −s/2)`
  for `refreshing || s > 0` (l.87). The gap's `.system` look is already centred (`s/2`), so the band now matches it. For
  `s ≥ L` nothing changes (`L/2` both).
- L2, band and overlay opacity while pulling: `min(1, max(p/L, dragPosition))` (l.100, l.109); overlay centre
  `−L/2 + L · min(1, max(p/L, dragPosition))` (l.105). `dragPosition = min(1, p/T)`, so with `T ≥ L` (every default) nothing
  changes; with `T < L` the look reaches the refreshing look exactly at the trigger.
- L3, `holdsPlacement` (l.184): `mode == .refreshing || (retract == .spinner && (!overlay || band))`: the band keeps the
  refreshing placement through a `.spinner` retraction for every style; removes the pre-existing `.default` band end step

### 3.4 Alternatives
- Centre only (no carry): the opacity step `1 → s/L` stays (host math above). Carry only (no centring): item 31 stays (10 pt at
  T 40) and the carried look ends at a lift / fire anyway (same placement), so centring is needed for item 31 alone.
- Keep the far-end pull look and animate the switch: the switch is a 7.5-25 pt move against the content; any animation of it

  always been centred; centring the band's makes the two collapse modes look the same, so no API option is proposed
  (question in section 9).

## 4. Interactions inside this design
- Item 32 needs item 33's catch: without it the engine sees the model's pull (0) at the re-grab and drops the carried look at
  once (17.5 `spikelook` without `spikecatch`: the same −15 pt step).
- The coordinator's `input()` uses `max(state pull, drawn pull)` while retracting; with the catch the two agree at the touch.
- Programmatic `beginRefreshing()` during a `.pull` retraction (pre-existing, rare): the leaf goes from the pull look
  (opacity `dragPosition`) to the refreshing look (1) unanimated. With L1 the position is the same for `.system`; the opacity
  step remains: section 6 step 5 animates the placement opacity with `modeAnimated` (the look's own 0.15 s cross-fade).

## 5. Item 27

### 5.1 Defect and cause
D66 (`RefreshResizeReveal`, `RefreshPlacementEffect.boxes`) hides an ungrouped indicator (15-16 or forced, custom
indicator, no scaling header: latched kind `.none`) during any resize that began with nothing of it visible and reveals it
in its own delayed fade (`.linear(0.15).delay(0.3)`) once the resize closes. Its premise (M8b-s6/s7, unchanged): the
indicator keeps no layer while its gap is off the viewport, a system rotation (Core Animation interpolating the final layer
tree) would draw it at once at its final place over the content still sliding in (item 20), and nothing in pure SwiftUI
tells that rotation from an instant resize. So an instant, unanimated resize also hides it for 0.45 s, and every rotation
that brings the gap back shows it 20 frames later than 17+ does.

Forced lane (27.0 `-ZTronForceAllFallbacks`, the lab's 20 pt white custom indicator, hold 60, no header, `holdgap.py`;

### 5.2 Design: the ungrouped gap indicator behind the content
- **What.** A gap (non-overlay) indicator that has no layer group (the latched kind `.none`) is drawn in a slot **behind**
  the content instead of the overlay slot above it. Whatever Core Animation draws during a system rotation, it cannot be
  drawn over the content: the content hides it until it has slid away; an instant resize draws it at once in its place, as
  17+ does. No hiding, so no signal is needed and item 27 has nothing left to distinguish. UIKit's `UIRefreshControl` is the
  scroll view's lowest subview (behind the content) too.
- **Slot** (`ScrollContainer`, ZTronScrollView.swift l.153, where the spike put it): `.background(RefreshOverlay(..., layer:
  .behind).ignoresSafeArea(.all, edges: edges))` right after the transform host, only when `!state.usesGeometryGroup` (fixed
  for the state's life: 17+ preferred builds the same tree as today). Behind the content and in the viewport's own frame,
  like the overlay slot; a `.slideBehind` header never coexists with it (the kind is `.none` only without a header).
- **One coordinator.** `RefreshHolder` moves from `RefreshOverlay`'s `@StateObject` to `ScrollContainer`'s (the
  `PanCoordinator` pattern, l.~103), passed to both slots. The front slot keeps everything that must exist once: the
  `onAppear` wiring (`pan.refresh`, announce, `apply`, reach watchers), `cancelAll` on disappear, the accessibility elements,
  the haptic. `RefreshIndicatorsHost(layer:)`: `.behind` lays out leaves only.
- **Which slot draws** is the leaf's latched decision, extended: `RefreshGroupLatched` already latches the kind at the boxes'
  first frame and keeps it while the boxes exist (the whole hold, the D39 animated reset included); a leaf draws its boxes
  only if `(kind == .none && !overlay) == (layer == .behind)` (`RefreshLayerMath.draws(layer:kind:overlay:)`, pure). Both
  slots carry the leaf on the ungrouped path; one draws, and installing a header or swapping the indicator during a hold
  changes nothing until the boxes are gone (no identity change while anything is drawn, as D66's gate today).
- **D66 is deleted** (`RefreshResizeReveal`, its `reveal` input and the `boxes(...)` gate). The only ungrouped leaves left
  in the front slot are overlay ones (they float over the content by design, so they cannot go behind), and D66 never hides
  them: measured at 09226f4, forced, `-hoverlay` (the probe floats at the base): drawn in every judged frame of the instant
  resize (62 / 62) and of the rotation (116 / 116; largest frame step 17.5 pt = 0.10 of its 174 pt travel with the window).
- **Blend modes**: behind the content the indicator composites with what is behind the scroll view, which is what the gap
  shows in the front slot too (the content is not under the gap): `RefreshUITests.testACustomIndicatorsBlendModeReachesWhatIsBehindIt`
  keeps yellow over the gap's blue (section `blend`) and magenta over the content (`blendOverlay`, front slot).
- **S4 / S7**: no content body re-evaluation (a background sibling of the content, render-time placement as today); the
  rotation keeps the visible centre (the slot does not move the content).

### 5.3 The 15-16 layer of a custom indicator: an option (contested behaviour)
`refresher(..., refreshView:, fallbackLayer: ZTronRefreshFallbackLayer = .preservesBlendModes)`, ignored on 17+ (the
geometry group is drawing-neutral there):
- `.preservesBlendModes` (default, D65 kept): no layer group on 15-16; the gap indicator is drawn behind the content (5.2).
  Blend modes reach what is behind the indicator as on 17+; rotations keep the two residuals above.
- `.layerGroup`: the built-in indicator's `compositingGroup()` on 15-16 (the existing `RefreshIndicatorGroup.Kind
  .compositing`, decided by the same latch): rotations as 17+ (the built-in indicator's measurements, open item 19); a blend
  mode inside the indicator composites within it (the blend test's `white` on that option).
Default: `.preservesBlendModes`, because D65 chose blend fidelity for headerless custom indicators; the question in
section 9 asks whether the default should be the rotation-faithful one (most custom indicators have no blend mode). The
option is a refresher-level value (`RefresherSpec`), resolved like `overlay`; `RefreshPlacementEffect.fallbackGroup` becomes
`hasHeader || !custom || spec.fallbackLayer == .layerGroup`.

### 5.4 Alternatives rejected
- **D66 as is**: item 27 (27 frames missing after an instant resize) and 20 frames missing after every rotation that brings
  the gap back (the 15-16 look differs from 17+).
- **A rotation signal**: none in pure SwiftUI (D66's premise); a heuristic (width and height swapped plus a safe-area
  change) misses Stage Manager / Split View resizes, which Core Animation interpolates too, and fires for an instant swap.
- **A layer group around 15-16 custom indicators** (keeps a layer off the viewport, item 20 as on 17+): isolates the
  indicator's blend mode (D65, the blend UI test); i29 found no 15-16 modifier that keeps a layer without isolating it.
- **Behind for overlay indicators**: they are drawn over the content by design.

## 8. Risks
- **The 17.x pin and app animations.** While a drawn-catch pin holds (at most the rest of the library's own reset
  animation, 0.35 s by default), an app-driven SwiftUI animation of the content effect's inputs (an inset animated by the
  app) is drawn at its final value. Ending the pin at that animated transaction instead would re-expose the reset's
  remaining residual for its frames (SwiftUI 17.x adds the two). Only 17.x (27.0 / forced end the pin at the first
  evaluation). To measure in step 3: an inset animation 0.1 s after a catch, 17.5.
- **Item 27, transparent content.** Behind the content, the indicator is hidden by opaque content (the lab's) during a
  rotation that brings the gap back; through transparent parts of the content it could be seen while the content slides
  over its final place. Unmeasured: step 4 adds a lab variant whose first row is clear (`-ZTronSeamClearFirstRow`) and
  `holdgap.py` counts the probe seen through it as over (threshold 0).
- **Item 27, a rotation's first frames (15-16, default option).** With `.preservesBlendModes` the two rotation
  residuals of 5.1 stay on 15-16 (pre-existing; fewer missing frames than 09226f4: top 27 → 7, leading 28 → 9 + 3 off); they
  are the option's trade, and `.layerGroup` (5.3) removes them (the built-in indicator's group, rotations as 17+). The
  rotate rows of section 7 are therefore judged per option; section 9 asks which default the user wants. If i29's sweep or
  the M1 lane finds a 15-16 boundary that keeps blend modes, the option collapses into it.
- **The header pin and i28's mix.** i28 moves part of the `.stretch` growth into the layout (`HeaderSlotLayout`, `m · g`):
  that part is pinned by key 4 already; any new animatable header effect must read `live.pinned(key)` too, or 17.5 shows
  the seam of 2.3 (3) again (the section 7 header row catches it).
- **The hoisted holder.** The front slot keeps the lifecycle (`onAppear` wiring, `cancelAll`); the behind host never reads
  `pan.refresh`; `RefreshUITests` (begin / end / announce / haptic serial) on every lane.
- **The 17.x rebase** changes only catches that move the presentation (the drawn catch): a clock catch adopts the
  presentation the environment already read. `PanSessionTests` cover both.
- **Found, out of scope (candidate open item 34, the trigger):** every pull-refresh run shows the content 11-18 pt further
  in one recorded frame at the trigger (27.0, `.preserve` and `.stretch`, T 40 and 60, 09226f4 and the spike alike), with a
  50-97 ms gap between the recorded frames there (load 50-390). The per-update log (`-spikelog`, l27e) shows no mapping
  jump: the finger's writes come every 16.7 ms at 2.7-2.8 pt, the trigger (`mode(.refreshing)`) is followed by one gap of
  78 ms (`.preserve` T 40: −330.51 → −344.55, 14.0 pt = five samples of finger travel) or 37 ms (`.stretch` T 60: 5.3 pt),
  then the 16.7 ms cadence again; the hold is not opened while tracking (`hold 0.0`). So it is a main-thread stall right
  after the trigger (load 80-180 here), and the recording shows the finger's travel during it. To profile on an idle
  machine (first `ProgressView`, the haptic, the announcement, the action's `Task`): not part of this design.

## 10. Interactions with the other M8b-s8 designers
- **i29-blend-slidebehind**: its G is for views with a header; the behind slot exists only without one (kind `.none`).
  Both read `RefreshGroupLatched`'s latched kind; the slot decision reads `.none` only, so a change of the 15-16 group under
  a header does not move any leaf between slots. Its doc keeps "D66 unchanged" for headerless 15-16 views: with this design
  D66 is gone and those indicators are behind the content (their no-header blend rows are the cross-check, with the blend
  UI test). Both edit `TransformHost` (i29 drops `hasHeader`; this design adds the pin's arguments) and the container's
  slot list around ZTronScrollView.swift l.151-190: the second to land rebases.
- **i28-stretch-blur**: L1 (the band's `.system` pull look centred) and L3 (`holdsPlacement` for every style) move the
  spinner in their `.stretch` band scenarios with `.system`: re-take their spinner positions after step 2. Shared code:
  `RefreshIndicatorMath.placement`, and the header pin of step 3 in `HeaderStretchEffect` / `HeaderStretchClip` /
  `HeaderSlotLayout` (one `live.pinned(key)` read each): whichever effect draws i28's mix reads it (8, risks).
- **d75-short-content**: d75 makes `ContentTransform.animatableData` carry the content's shape (its pad) and adds the
