# USER-s5 handoff · 2026-10-21 · Sonnet 5.5 builder (user report: the refresher on a slow pull)
Status: done — root cause found and measured on 27.0 and 17.5, fixed in the engine, regression tests at three levels. Not done on purpose: the indicator still disappears at once at the end of a refresh and at a release (both speeds), see Open 1.
Report (user, verbatim): "Refresher doesn't work as it should. It inconsistently shows the progress indicator: specifically if I have a purely vertical scrollview and I pull down slowly, the refresh triggers but only the final part of the view shows."
Root cause (D35): the display depended on the speed of the pull. The reveal was never the problem: with a DEBUG trace of what the leaf draws (27.0 iPhone 18 Pro clone and 17.5 iPhone 15 Pro, built-in `.default`, custom `refreshView` and `.system`) the visible thickness is exactly `min(pull, indicator height)` frame by frame and the whole 60 pt is shown when the trigger fires (pull 100.4), slow or fast. What changed with speed is where the lift falls relative to the action (0.6 s in the demo, any real call in the app): a slow pull outlives it. The engine then handled `done` in `.triggered` by going idle at once: the spinner turned into the pull ring (`mode .notRefreshing`, "Refresh complete" announced under the finger), the next sample re-entered `.pulling`, and the lift found nothing to hold, reset to 0 and the leaf was gone while the content was still pulled 110 pt. A fast pull lifts first, the hold opens and the spinner is shown for the minimum visible time. M8b-1 and M8b-2 had both written this path down as "the hold never opens" without looking at what it shows.
Trace before the fix (slow, default section, 27.0 and 17.5 identical): `fx mode(refreshing) pull=100.4` → `trigger` → `leaf mode=refreshing vis=60` → `ev done … phase=triggered` (tracking) → `fx mode(notRefreshing)` + `announce("Refresh complete")` → `leaf mode=notRefreshing vis=60` (ring) → `fx mode(pulling)` → `ev lift … phase=pulling` → `fx mode(notRefreshing)`; no `hold` at all. After: `trigger` → `ev done … phase=triggered` (nothing changes) → `ev lift` → `fx mode(notRefreshing)` + announce at the lift. Fast pull (unchanged): `trigger` → `lift` → `hold(60)` → `done` → `clearHold` after the minimum visible time.
Changed:
- `Refresh/RefreshEngine.swift`: `.triggered` + `done` no longer ends the refresh: `returnedUnderFinger`; at the lift / sequence end / a sample with the finger up `endTouchWhileTriggered` decides: nothing held when the indicator has been refreshing for `minimumVisibleTime` since the TRIGGER (`triggeredAt`), else the hold opens and the phase is `.finishing(until: triggeredAt + minimumVisibleTime)`. An action still running at the lift: unchanged (`.refreshing(since: lift)`).
- `Refresh/RefreshIndicators.swift` + `RefreshCoordinator.swift` (DEBUG only): `RefreshTrace` writes what the leaf drew (a line when the visible thickness to 0.5 pt, the mode or the progress changed) and every engine event / effect into the shared `ZTronRenderCounters` event log; `RefreshPlacement.visibleLength(vertical:)` (frame ∩ clip) is shared with the tests.
- Demo `RefreshScreen`: `refresh.trace` (the refresher lines of the event log, capacity 600, read with `Info`).
- Tests: `RefreshEngineTests` (3 pure tests replace the one that pinned the old behavior: returns under the finger, lift before the minimum visible time, sequence end / missing lift), new `RefreshSlowPullTests` (frame-by-frame visible thickness at 6 / 40 / 160 frames × `.default` / `.system` × both OS paths; the slow pull keeps the refreshing look until the lift; a quick lift holds for the missing time), `RefreshUITests.testASlowPullShowsTheWholeIndicatorUntilTheLift` (default / custom / system, `.slow` velocity, 1.5 s hold) and `testAFastPullShowsTheSameIndicator` — they read the trace: revealed in proportion to the pull, whole at the trigger, still refreshing under the finger.
Decisions (USER5-n; the rule itself is D35):
1. Parity target = `UIRefreshControl` (S9 "animate back to rest unless the user is tracking"): a refresh that ends mid-drag stays on screen until the touch ends. `endRefreshing()` / `done` during a drag behave alike.
2. The minimum visible time is counted from the trigger when the action returned under the finger (the indicator has been on screen since then); when the action is still running at the lift it keeps its meaning "from the moment the hold opens" (M8b-1 Decision 4). A fast pull with an instant action now holds for what is missing to 0.5 s from the trigger, not 0.5 s from the lift.
3. No change to the reveal, the placement formulas, the hold geometry or the leaf lifetime: smallest fix. The probe is the oracle for the next report: `Info` → `refresh.trace`.
4. Simulators: private devices (`simctl clone` of the 27.0 iPhone 18 Pro; the 17.5 iPhone 15 Pro clone failed twice with "stuck in creation state", so a fresh `simctl create` iPhone 15 Pro was used), deleted afterwards; unit runs and the red check in detached worktrees at HEAD + this change (the shared checkout had other sessions' edits).
Open:
1. **The indicator does not retract with the content.** At the end of a refresh (the mode and progress reset on the same frame as `clearHold`) and at a release below the trigger or after an early return, the leaf (alive only while `mode != .notRefreshing || dragPosition > 0`) disappears at once while the content is still sliding back; `UIRefreshControl` keeps the spinner glued to the content edge until the gap closes. Same for both speeds, so not part of this report. Proposed: engine phase `.retracting` (progress follows the live pull to 0, then idle; the coordinator already samples while a phase is active), a display-only "refreshing look" for the built-in indicator after a completed refresh, custom views see `mode .notRefreshing` with a decreasing `dragPosition`, overlay style slides out as today; the end condition must not use "settled and not tracking" (the first flush after the lift runs before the release motion starts).
2. Not reproduced and not claimed: a custom `refreshView` taller than `configuration.indicatorHeight` is framed to that height (clipped / squeezed), and a `triggerDistance` smaller than `indicatorHeight` shows only the bottom `triggerDistance` of the indicator when it fires (design, `.default` is glued to the content edge). If the user's view is one of these, the answer is the configuration, and it is worth a line in the API docs.
3. Real device: the trace shows the same numbers on both simulators; the feel (spring-back after a slow release, the haptic moment) is still R1–R3 of M8b-1.
