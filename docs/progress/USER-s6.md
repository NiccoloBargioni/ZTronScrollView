# USER-s6 handoff · 2026-10-21 · Sonnet 5.5 builder (follow-up of USER-s5 / D35, Open 1: the refresh indicator retracts with the content)
Status: done — the indicator no longer disappears on the frame the progress resets: after a release below the trigger, at the end of a refresh and after an early-return release (D35) it goes back with the content until the gap is closed. Measured on 27.0 and 17.5 (trace of what the leaf draws), unit and UI green on both. Not done on purpose: the feel on a device (R1–R3 of M8b-1 are still the user's).
Why (visual polish, not the user's report): `UIRefreshControl` keeps the spinner glued to the content edge until the gap closes. Here the engine went idle (progress 0, mode `.notRefreshing`) and the leaf, alive only while `mode != .notRefreshing || dragPosition > 0`, was removed on that frame while the content was still sliding back.
Changed:
- `Refresh/RefreshEngine.swift`: phase `.retracting(RetractLook, until:)` and effect `.retract(look?)`, entered where the engine used to go idle with the content still pulled (> 0.5 pt, `retractedPull`): a lift below the trigger or a cancelled one (`.pull`), `finish` at the lift or by `resetAnimation` (`.spinner`), the early-return release of D35 (`.spinner`). `mode` is `.notRefreshing` meanwhile, `progress` follows `pull ÷ trigger`. Ends at pull ≤ 0.5, at `until` (3 s, `retractTimeout`, safeguard) or when a new pull takes over (a lift on it may fire; `begin` is not swallowed; `cancel` and a disabled edge end it). Not entered for `sequenceEnd`, a missed lift, a disabled edge, `resetAnimation: nil`, or when the pull is already gone.
- `Refresh/RefreshCoordinator.swift`: `retractions[edge]` (the look, display only), the `.retract` effect, the animated batch (below), `Input.pull = max(state pull, last drawn pull)` while retracting, and a 30 Hz beat (`heartbeat`) when the frame clock is idle.
- `Refresh/RefreshIndicators.swift`: the leaf lives while `retractions[edge] != nil`; `RefreshPlacementEffect` (`ViewModifier & Animatable`, `pull` = `animatableData`, `nonisolated` type with a `@MainActor` body) draws the placement; `BuiltInRefreshIndicator(spinner:)` keeps the spinner after a refresh; DEBUG trace lines carry `look=`.
- `Refresh/RefreshTypes.swift`: doc comment of `dragPosition` only (no API change).
- Tests: `RefreshRetractTests` (new, 21: 10 pure engine, 11 through the pan / state / coordinator on both OS paths incl. leading and bottom edges, an overlay edge, a hosted SwiftUI-animated reset), `RefreshEngineTests` (5 expectations moved to the new behavior), `RefreshSlowPullTests`, `RefreshRig` (`visibleIndicator`, `retractFrames`, `retractLook`).
- Demo / UI: `RefreshUITests.assertTheIndicatorRetracts` on the slow and the fast probe, new `testAPullLetGoBelowTheTriggerRetractsWithTheContent` (default / system / custom); `refresh.trace` capacity 1000.

Decisions (the proposal of USER-s5 Open 1 was checked; one deviation, with its measurement):
1. **The proposed "progress follows the live pull" cannot see the default reset.** `resetAnimation` defaults to `.swiftUI(.easeOut(0.3))`: the clear is `withAnimation { setRefreshHold(followsOffset: true) }`, whose inset-only rule `writeBoth`s target AND presentation, so the state's offset JUMPS to rest in the call while SwiftUI draws the content back. Measured on 27.0 (temporary probe in a scratch worktree, fast pull, default section): `pres = 0` at +0 ms, `drawn` (the content effect's probe, `state.probe.pending`) `-60` until +50 ms, `-49.3` at +100, `-22.6` at +200, `-0` at +400; `clock=false`, `phase=idle`, 61 samples before and after (none during). A leaf that reads the state's pull draws 60 → 0 in one step. The clock-driven cases (release pipeline after a lift, `.uikit` reset) do move the presentation per tick and are sampled as proposed.
2. So, for the SwiftUI-animated reset: (a) the leaf draws through an animatable placement and the retraction's effects are applied inside ONE `withAnimation(resetAnimation)` (the hold clear, the mode, the progress, `.retract`), so SwiftUI interpolates the indicator in the same transaction as the content: exact glue, same curve, no polling for the motion itself; (b) while an edge retracts the engine's pull is `max(state pull, last drawn pull)` and a 30 Hz beat samples it when `state.isClockRunning` is false, so the engine ends when the DRAWN content is at rest, not on a guess of the animation's length (SwiftUI exposes no duration; a deadline would cut a long reset or linger on a short one). The beat stops with the retraction; the 3 s deadline covers a content that is never drawn.
3. The end condition is NOT "settled and not tracking" (the first flush after the lift runs before the release motion starts): pull ≤ 0.5, takeover, deadline. Pinned by a pure test (`sample(70, tracking: false, settled: true)` right after the lift changes nothing).
4. Built-in look: `.pull` (ring / arrow with the falling progress, `.system` fades with it), `.spinner` after a completed refresh (display-only override passed to the leaf; `ZTronRefreshState` is unchanged: `mode .notRefreshing`, `dragPosition` falling). Custom views see an idle edge with a falling `dragPosition` (a staircase at 30 Hz in the SwiftUI-animated reset: their own animatable properties interpolate between the steps if they use an implicit animation). The overlay style keeps its formula (`center = −L/2 + min(pull, L)`): it slides out with the pull, it does not pretend to be refreshing.
5. `ZTronRefreshState.dragPosition` no longer snaps to 0 with `mode` at the lift / the end of a refresh: it falls to 0 over the retraction (doc comment updated; an app that gates its own UI on `dragPosition > 0` keeps it for that long).
6. Swift 6: `RefreshPlacementEffect` is a `nonisolated` struct with a `@MainActor func body` (a `ViewModifier & Animatable` otherwise fails "conformance … crosses into main actor-isolated code"; the compiler's other suggestion, an isolated `@MainActor Animatable` conformance, was not taken: SwiftUI reads `animatableData` off the main actor).
7. Verification: edited in a detached worktree at f8ed310, then re-verified in a second one at c19bb2e (main with DBG-s6) + the patch; private simulator clones of the 27.0 iPhone 18 Pro and the 17.5 iPhone 15 Pro (both `simctl clone` worked this time), deleted at the end.
