# DBG-s4 handoff · 2026-10-21 · Sonnet 5.5 · Debugger (touch-based UIKit controls under the always-on observer on 26+, DBG-s3 Open 2)
Status: done. Four of the six control families (Stepper, segmented `Picker`, compact `DatePicker`, `ColorPicker`; five of the nine interactions) never reacted to a tap on 26.0 / 26.5 / 27.0 with the always-on `SpatialEventGesture` observer; measured with a UIKit probe, fixed (**D36**: `SpatialEventGesture` from iOS 28, 18.x to 27.x take the armed `DragGesture` row), 9 new demo UI tests red without / green with the fix on 27.0, green on 26.0, 26.5, 18.5, 17.5 on both paths. Closes (b) of Orchestration open item 11. **D36 narrows the user amendment "iOS 26+ keeps `SpatialEventGesture`" (narrowed to 26 by D34, which the user confirmed on 2026-10-21, before this was measured) and needs the user's confirmation (Open 1).** Two limitations of the pure-SwiftUI pan turned up on the way (Open 2, Open 3): not caused by the observer, not fixed here.

Root cause (UIKit probe in a scratch copy of the tree: `UIControl` events + `UITouch.gestureRecognizers` at every touch phase; probe, logs, runners in the notes folder `controls-26x/`):
- On 26.0 / 26.5 / 27.0 the observer's SwiftUI recognizer (`UIKitResponderGestureRecognizer`, `cancelsTouchesInView = true`, the `SpatialEventGesture` one) begins at the **touch-down itself**, not with the first movement as on 18.x (DBG-s3). UIKit then withdraws the touch from the hit view before its `touchesBegan`, and the control's own non-simultaneous recognizers are blocked.
- Stepper tap, 27.0, observer attached (`diag-stepper-270-preferred.log`): `touch began hitView=UIStepper`, no `CTRL UIStepper event touchDown` at all, `touch ended hitView=nil` with the observer recognizer at `st=1` (began). Observer detached (`--forced`, `diag-stepper-270-forced.log`): `touchDown` 17 ms after the touch, the recognizers end `st=5` (failed), `valueChanged` + `primary` + `upInside` at the lift, the value moves.
- Controls that survive are recognizer-based on these OSes: Slider and Toggle (DBG-s3), `Menu` (`HostingUIButton` with `_UITouchDownGestureRecognizer` / `_UISimplePressGestureRecognizer`), TextField, SwiftUI `Button`. The ones that die are touch-based (`UIStepper`, `UISegmentedControl`) or tap-recognizer-based and blocked by the recognizer that already began (compact `UIDatePicker`'s `UIButton` with `UITapGestureRecognizer`, `UIColorWell`).
- D34's 18.x slider and this are the same recognizer: drag case there (begins with the first move), tap case here.

Decisions:
- D36: `SpatialEventGesture` unused below iOS 28. The smallest change that makes the controls work, no new UIKit, no new spec row; the alternatives are below. The 26+/27 pinch is back on the 17 row's documented divergences (centroid = `startLocation` + drag follow, one-finger lift ends the pinch, touch-down at rest waits for the first drag sample); preferred equals forced on those OSes now, and the forced demo UI lanes were already the 27.0 picture of DBG-s3.
- Not taken, need the user: (b) keep `SpatialEventGesture` only for zoomable scroll views (always-on there, armed like the fallback elsewhere): keeps the exact centroid where pinch needs it, but a zoomable view with a Stepper or a segmented `Picker` stays broken; (c) the D31 UIKit touch observer on 26+ too (SPEC S2 exception widened; passive recognizer, cancels nothing): keeps touch-down at rest, live centroid, count (the user did not want it on 18.x in D34).
