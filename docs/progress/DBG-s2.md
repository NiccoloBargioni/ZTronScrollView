# DBG-s2 handoff · 2026-10-20 · Sonnet 5.5 · Debugger (M6 s3 regression: `PanUITests.testControlsUsable` on iOS 17.5)
Status: done. The regression found by the M8-1 integration run (red on 17.5, both paths, since 8ad77c2) is fixed: root cause measured, smallest patch, regression test. Fix + test = commit e8c5674 on `claude/determined-lederberg-7907ea` (parent main dbee893); this handoff and the Orchestration/STATE lines are the two commits after it.

Root cause (measured with temporary logs, confirmed by one-variable experiments; the patch with the logs is in the notes folder):
- Bisect of 8ad77c2's `ScrollContainer.body` additions on a private 17.5 clone (5 runs each, preferred): the four modifiers removed 5/5 · `.modifier(PositionTicket)` alone 0/5 · ticket on a background leaf + `.transaction` + `onAppear` + `onChange` 5/5. Only the `GeometryEffect` WRAPPING the container matters (identity transform, ticket constant 0: this screen has no binding). `.transaction`, `onAppear` and `onChange` are innocent.
- The focused field is never re-hosted (same view chain, `window` non-nil at `textDidEndEditing`). UIKit's stack there: `-[UITextField resignFirstResponder]` ← `-[UIView setUserInteractionEnabled:]` ← SwiftUI's display-link update. SwiftUI disables the field's user interaction because `TransformHost` sets `.allowsHitTesting(!blocked).disabled(blocked)` and `blocked` turned true.
- Why `blocked` (library trace, 17.5): tap → `BEGIN editing` → `UIKeyboardWillShow`. With the wrapper SwiftUI interpolates the keyboard-avoidance layout per frame (the viewport observer reads y 262 → 250 → 238 → …) and its first update pairs the new keyboard inset with the OLD frame: raw size 360, `safeAreaInsets.bottom` 230, frame still at y 262. `ViewportObserver` adds the ignored inset (viewport 590), `applyViewport 360 → 590` opens a resize, `resizeTick` finds the effect still drawing at 360 → `writePhase(.animating)` → `blocked` → resign → `UIKeyboardWillHide` 30 ms after `WillShow`; the layout that had started to move goes back (the evidence frames).
- Without the wrapper (before 8ad77c2, or with the leaf) the avoidance is one committed frame: y 94, bottom inset 0, no `applyViewport`, no `.animating`, nothing blocked.
- The bug is not "iOS < 18": at dbee893 the new test is red 3/3 on 17.5 AND on 18.5 (same "Neither element nor any descendant has keyboard focus"); 27.0 passes (not measured why). The fix is green on 17.5, 18.5, 26.5 (testControlsUsable), 27.0.

Changed:
- `Position/PositionDriver.swift`: new `PositionTicketLeaf` (a clear view carrying `PositionTicket`, with the root cause in its doc comment); `PositionTicket` doc says to use the leaf.
- `ZTronScrollView.swift` (`ScrollContainer.body`): `.modifier(PositionTicket(ticket:))` → `.background(PositionTicketLeaf(ticket: ticket))`, same place in the chain, above `.transaction`.
- `Demo/ZTronScrollViewDemoUITests/PanUITests.swift`: regression test `testFocusedTextFieldKeepsKeyboardThroughAvoidance` (tap, type, 1.5 s pause, type again, value "ab", scroll view idle). Red 3/3 at dbee893 on 17.5 and 18.5, green with the fix.
Decisions:
- The ticket stays an animatable effect (M6 s3 needs it: `withAnimation { position = … }` reaches the container only through an animating descendant); it moves from wrapper to leaf, which `.transaction` still sees. Nothing else changes, so M6 s3's semantics are untouched (PositionTests, TargetsUITests, ProofUITests green on both OS paths).
- NOT hardened here (smallest patch): the library is still fragile to ANY ancestor effect, measured with the fix in place on 17.5 (demo ControlsScreen with an app-level wrapper around the scroll view, new test ×3): none 3/3, `.offset` 3/3, `.compositingGroup` 3/3, `.scaleEffect(1)` **0/3**, `.rotationEffect(.zero)` **0/3**. One-line experiment, not committed: `TransformHost`'s `blocked` without the resize watch (`phase == .animating && !metrics.resize.isOpen`) → the scale and rotation wrappers pass 3/3 each, with the scroll view idle at `y=0` afterwards. It changes M3b's catch semantics (a touch during a resize would also reach the content), so it is a design call for Open 1, not a regression fix.
Open:

Latent, pre-existing (M3b gate, 8878a99): `TransformHost` blocks content with `allowsHitTesting(false)` + `.disabled` in `.decelerating` / `.animating` / dragging, and that resigns a focused UIKit text field. Measured: a resize watch (this bug) and a plain DRAG on the scroll view with the field focused (temporary test, 0/3 on 17.5 and 0/3 on 27.0: `keyboards.count` 0, "Neither element nor any descendant has keyboard focus"), while the same content in a native `ScrollView` keeps the focus (3/3 on both); an animated scroll takes the same path (not measured). It contradicts M8-chrome §4 (`.automatic` = `.never`; "<17: no public way to resign focus"). For the M8 keyboard session: (a) block touches without disabling the content (a hit-absorbing overlay above it) so focus survives, which also fixes the wrapper case; (b) at least keep the resize watch's `.animating` out of `blocked` (the experiment above passes; re-run `ResizeUITests`) and treat a (size, inset) pair that moves in lockstep as an inset change. Apps that wrap a `ZTronScrollView` in `.scaleEffect` / `.rotationEffect` hit the resize case today on 17.5; the notes folder has the experiment patch (`controls-175-keyboard/experiments-wt-exp.patch`).
