Decisions:
1. Members and twins both write recipes (`ObserverDescriptor`), not boxes: a member is a plain value call in the parent's body (a fresh box per body would re-seed and re-fire the initial call), and a twin above several scroll views needs one box per scroll view (`last` is per box). The container keeps the boxes in an `ObserverStore` keyed by the twin's `@State` token / the member's position; the owner's body re-assigns the closures every evaluation (R7), measured by T4 (member + twin).
2. Q1 measured (27.0, native `ScrollView` vs ours in `theInitialCallIsAValueValueCallLikeNative`): native reports `0.0->0.0` before layout, then `0.0->-62.0` once the safe area lands; ours registers after the viewport commit and reports `-62.0->-62.0` once. Same final value, one call fewer; kept (matching a pre-layout call would mean firing from `body`). The hub itself fires `(v, v)` at registration whatever the size (geometry boxes have no size gate; the frame-based ones wait for a container size).
3. Q4: the unprefixed members `onScrollGeometryChange` on `ZTronScrollView` and SwiftUI's 18+ `View` extension share one chain without ambiguity (the concrete type's member wins; the test chains two unannotated closures and checks both bound to the member). Shipped unprefixed.
4. Rest is NOT offset 0 under a safe area: the visible rect of a viewport that spans the safe area starts at `-inset` (so with a 62 pt bar the second 100 pt item of a 200 pt view shows 38 % at rest). `visibleRect` is therefore the container rect, as in native.
5. The visibility modifier does not reuse `ScrollFrameReporter` (it is bound to the registry's ids); it mirrors its two branches with its own preference key. A refactor to one generic reporter is possible when M6 s3 is done with `ZTronScrollID.swift`.
6. The 17+ branch of the twin wraps the main-actor transform in an `@unchecked Sendable` box (`UncheckedTransform.run`, `MainActor.assumeIsolated`), like `ZTronBridgedScrollTargetBehavior`.
